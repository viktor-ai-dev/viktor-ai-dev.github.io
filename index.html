E-Commerce Customer Intelligence Platform

End-to-end cloud data platform that transforms raw e-commerce transaction data into trusted, analytics-ready business intelligence. The platform combines automated ingestion, cloud storage, BigQuery, dbt, dimensional modeling, data quality testing, orchestration and an interactive Streamlit dashboard.

E-Commerce Customer Intelligence Platform Architecture

Business Problem

Raw e-commerce transaction data is difficult to analyze directly and is spread across multiple source datasets. The platform transforms these sources into governed, analytics-ready data for revenue, product, customer and retention analysis.

End-to-End Data Pipeline

1. Ingestion
Raw CSV datasets are converted into Parquet for efficient analytical storage.

2. Cloud Storage
Parquet datasets are uploaded to Google Cloud Storage.

3. Warehouse Ingestion
BigQuery External Tables provide warehouse access to the cloud-hosted datasets.

4. Transformation
dbt builds the analytical warehouse through staging, dimensional and reporting models.

5. Analytics
Business-ready reporting models are consumed by an interactive Streamlit dashboard.

Technology Stack

Python SQL PySpark PyArrow Parquet Google Cloud Storage BigQuery dbt Kestra Docker Streamlit Jupyter

Data Warehouse Architecture

The warehouse follows a layered dbt architecture that separates source preparation, dimensional modeling and business-facing analytics. This creates clear model responsibilities, reusable transformations and a scalable foundation for downstream reporting.

Staging Layer
Standardizes and prepares raw source data through type normalization, naming conventions and source-level transformations.

stg_customers • stg_geolocation • stg_order_items • stg_order_payments • stg_order_reviews • stg_orders • stg_product_category_name_translation • stg_products • stg_sellers

Dimensional Layer
Provides reusable business dimensions for analytical queries and downstream fact models.

dim_customers • dim_date • dim_payment_type • dim_products • dim_sellers

Fact Layer
Captures transactional and event-level business activity at explicit grains for revenue, order, payment and review analytics.

fct_order_items • fct_orders • fct_payments • fct_reviews

Reporting Layer
Transforms the dimensional warehouse into business-ready datasets optimized for KPI analysis and dashboard consumption.

rpt_customer_metrics • rpt_customer_retention • rpt_product_performance • rpt_sales_by_category • rpt_sales_daily

Architecture Flow
Raw Source Data → Staging → Dimensions & Facts → Reporting → Dashboard

Data Quality & Validation

Data quality is treated as part of the data platform rather than as a final validation step. dbt tests cover uniqueness, not-null constraints and relationships across the analytical models.

Business-level reconciliation was also used to validate revenue, order counts, customer mappings and product relationships across the fact and reporting layers.

Pipeline Orchestration

Kestra orchestrates the platform as a sequence of dependent workflows, separating ingestion, warehouse creation and dbt transformation responsibilities.

Current Flow
csv_to_parquet → upload_parquet → create_ext_tables → dbt_create_stg_tables → dbt_create_marts

The final marts workflow builds the dimensional, fact and reporting layers consumed by the dashboard.

Key Engineering Decisions

Parquet reduces the size of analytical files and provides a columnar storage format suited for warehouse ingestion.

BigQuery External Tables provide a cloud-native ingestion layer between object storage and the analytical warehouse.

dbt separates transformation logic into version-controlled, testable and reusable models.

Star Schema separates measurable business events from descriptive dimensions and simplifies analytical consumption.

Kestra handles workflow dependencies and orchestration while dbt remains responsible for data transformation logic.

Streamlit provides a business-facing consumption layer without moving transformation logic into the dashboard itself.

Project Scale

5 dimension models

5 reporting models

The reporting layer was validated against the underlying fact models to ensure consistent revenue and order metrics throughout the analytical pipeline.
